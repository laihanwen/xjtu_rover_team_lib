## 当前仓库也需要核查的问题

1. `firmware/stm32/MDK-ARM/Mate.c:158` 仍调用 `h30_configure()`，其中 `imu.c:74` 使用标为临时值的输出位图。桌面版已注释调用，并记录现场观察到欧拉角停更。源码能确认调用差异，具体 H30 位图和响应必须核对设备协议与实测，不能仅凭注释认定协议含义。建议首先改为可配置的“监听已配置设备”，并增加启动后有效欧拉帧检测。
2. 当前深度缓存有效期250 ms；参考代码注释给出 M10 0.5–1 Hz。若实测成立，直接接入会反复超时、无法持续 ARM。应优先确认/提高设备更新率；若设备只能慢速更新，再按控制需求设计独立超时与降级策略，不统一放宽 IMU/命令超时，也不能重复提交同一读数伪造新鲜度。
3. 当前漏水/kill 输入仍需实际接线调用 `AuvLink_SetSafetyInputs()`；深度驱动未绑定。已有安全门会因此阻止 ARM，这不是通过禁用安全门解决的集成问题。
4. 当前 Pi 目标分支 Fz 保持零，已有协议 depth target 不等于已实现定深。需要接入有效深度采样及底层控制后才可宣称功能完成。

## 推荐串口与链路方案

当前 UART1=H30、UART2=兼容遥控、UART3=Pi CRC；参考工程 UART3=M10。不能把两个接收回调或两根 TX 直接并到一起。

优先方案：保持 UART1/H30 和 UART3/Pi CRC，在确认 PC 遥控全部经 Pi CRC 接入后，把 UART2 改作 M10；这会移除 UART2 的旧0xA5硬件兼容入口，需要同步调整 CubeMX、USER CODE 回调、文档和测试。

替代方案：保留全部现有 UART 分工，通过经过确认的其他 UART/I2C 或 Pi USB-UART 接 M10。后一方案需扩展“带原始采样时间与有效性”的深度输入接口，STM32 仍负责定深闭环；当前协议不能未经定义直接复用。额外引脚、信号电平和传感器输出能力均待实物确认。

PC → Pi 遥控接入层 → 现有 auv_stm32_bridge → STM32 控制源仲裁/安全门 → PID/八推输出。遥控与 Mission 必须有明确互斥模式。0..255 摇杆量不能直接当 m/s；映射和速度上限需配置。现有协议的高层运动目标不能完整表达旧遥控的全部 heave/开关语义，缺失能力应明确扩展版本、两端解析及黄金向量。

保留上行 STATUS/IMU/DEPTH，限频与有界队列处理。参考版100 Hz回传14字节约1400 B/s；115200 8N1理论约11520 B/s。仅按源码字节量不能认定串口带宽耗尽，实际卡死需排查阻塞send/打印、无界缓存及线程生命周期，不应永久删除遥测作为修复。

## 补充：电机标号与遥控器说明核验

对照新增的 `电机标号.txt`、`遥控器对应.txt` 后，发现说明本身存在版本冲突，不能作为直接修改固件的授权或唯一事实来源。

### 电机表

八路 GPIO/定时器通道与两套固件的 PWM 写入及当前 tim.c 引脚映射一致。
但位置表的 T3=左前下、T4=右前下，与两套 Move.c 的坐标恰好相反：代码 T3=(180,-120,-58)，即右前下；T4=(180,120,-58)，即左前下（+Y向左）。其余六路左右/前后/上下标注一致。

这不是仅更改注释就能解决的问题：若实物按文本接线，现有分配矩阵中的 T3/T4 几何列可能与实物不匹配，导致合力/力矩串扰。先拆桨逐路确认 PB0/TIM3_CH3、PB10/TIM2_CH3 对应实物及推力方向，再决定交换接线、输出映射或重建几何列；不能仅翻转极性代替纠正位置。此表没有提供推力轴向或正反转信息，仍无法确认 T2/T3 极性或1488/1492中位选择。

因此“四个摇杆方向符合说明”只能确认到接收通道层。Fy在代码中采用 RC[8]-RC[7]（正字节偏移产生负Fy），Mz采用 RC[1]-RC[2]；是否符合物理左/右操作还依赖缺失发送端的符号转换及真实电机安装。速度SC=0/1/2也不是简单全轴慢/中/快三级，而是同时改变前后、横移和偏航权重。

下一步优先锁定 T3/T4 实物编号，并补齐发送端，离线输出每个轴/按钮对应的11字节帧。统一发布一份按固件版本区分的映射表后再实现合并；此次未修改原始两份文本或控制代码。

### 补充树莓派代码与双相机
